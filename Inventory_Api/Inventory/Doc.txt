// Database SQL via Entity Framework 
https://makolyte.com/ef-core-how-to-create-a-database-and-a-table/#Install_the_EF_Core_nuget_packages
à la racine du projet :
dotnet add package Microsoft.EntityFrameworkCore.SqlServer
dotnet add package Microsoft.EntityFrameworkCore.Design

The dotnet ef tool is used to install and update the database:
dotnet tool install --global dotnet-ef

Création initiale de la DB :
dotnet ef migrations add InitialCreate
	> crée un dossier Migrations
dotnet ef database update
    > applique le fichier migration_newName.cs à la DB (création de la DB et des tables)

Si erreur "la table xxx existe déjà", ça veut dire que le script tente de faire un CREATE TABLE d'uen table qui existe déjà :
    dotnet ef migrations list
    > regarder les migrations "PENDING" (= pas encore appliquées à la DB). 
    > Il devrait y avoir une migration "InitialCreate" qui n'a pas été appliquée à la DB. 
    > Si c'est le cas, il faut aller dans la BD __EFMigrationsHistory (View Data) et ajouter ou supprimer la ligne correspondant à la migration qui pose problème.
    > puis refaire dotnet ef migrations list et vérifier que le "PENDING" a disparu.
    > puis relancer dotnet ef database update

Erreur : "Une erreur liée au réseau ou spécifique à l'instance s'est produite lors de l'établissement d'une connexion à SQL Server. Le serveur est introuvable ou n'est pas accessible. 
Vérifiez que le nom de l'instance est correct et que SQL Server est configuré pour autoriser les connexions distantes. (provider: Fournisseur de canaux nommés, 
error: 40 - Impossible d'ouvrir une connexion à SQL Server)"
> revoir "DefaultConnection": "Server=(localdb)\\MSSQLLocalDB;Database=InventoryDb;Trusted_Connection=True;TrustServerCertificate=True"

Voir la DB (local) :
la base est stockée dans l’instance LocalDB MSSQLLocalDB.
Dans Visual Studio : Ouvre Affichage > Explorateur d'objets SQL Server.

Voir la DB (azure) :
go to the SQL database module > query editor

Update the DB (local) :
changer manuellement

Update the DB (azure) :
dotnet ef migrations add newMigrationName
push on GitHub
le workflow GitHub action prendra la migration la plus récente pour la push sur azure SQL

// déplacer un sln 
Suppose you currently have:
MyApp/
└── Project/
    ├── Project.sln
    ├── Project.csproj
    └── Program.cs

Target layout:
MyApp/
├── Project.sln
└── Project/
    ├── Project.csproj
    └── Program.cs

From the MyApp folder, run:
mv Project/Project.sln .
dotnet sln Project.sln remove Project.csproj
dotnet sln Project.sln add Project/Project.csproj

/ Swagger versus Postman
Swagger UI is useful when you want documentation tied directly to the API code. 
Postman is more focused on manually creating and organizing API requests.
Swagger:
    Automatically documents endpoints
    Shows the API contract
    Lets you try requests interactively
    Can support client-code generation
Postman:
    Offers advanced request collections
    Supports complex testing workflows
    Is useful for manually testing many services
A common workflow is to use Swagger for API documentation and basic testing, and Postman for more advanced testing.
